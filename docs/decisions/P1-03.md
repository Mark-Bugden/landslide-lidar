# P1-03 decisions: fetch scripts for rows 1–4 and the provenance check

Results: `results/provenance.json` (written by `scripts/provenance_check.py`); summary in `docs/provenance.md`.

## D03 · Sheet geometry in EPSG:5514

- **Decision.** The surveyed sheets (row 3, EPSG:4326) are reprojected with
  `pyproj.Transformer.from_crs("EPSG:4326", "EPSG:5514", always_xy=True)`, PROJ's default operation, applied vertex by
  vertex (`shapely.transform`). Edges are not densified. A sheet's "bounds in EPSG:5514" are the bounds of the
  reprojected polygon. Code: `landslide.sheets.load_sheets`, `transformer_4326_to_5514`.
- **Why.** PLAN.md §6 D03 default. BRIEF.md note 1 says "the sheet's bounds in EPSG:5514" without naming a method.
- **Alternatives.** Densifying the edges before reprojecting (the exact image of the lon/lat rectangle); a fixed
  Helmert variant instead of PROJ's per-area choice. Neither was needed: the default reading reproduces all 860 grids.
- **Evidence.** [E] pyproj 3.8.0, PROJ 9.8.1, network off, no grids needed. The default operation is not one
  fixed transformation. PROJ picks, point by point and by area of use, among four S-JTSK ↔ WGS 84 Helmert variants. Of
  the 1,320 distinct sheet vertices it transformed 824 with "S-JTSK to WGS 84 (5)", 493 with "(4)" and 3 with "(3)"
  (inverse, then Krovak East North). The pipeline strings are in `results/provenance.json` (`reprojection_D03`).
  [E] The recipe grids equal `fetch_log.jsonl` and each raster's own transform and size for 860 of 860 sheets.
  [E] Forcing one variant for all vertices instead (a one-off check, not part of the pipeline) reproduces only
  600 (variant 5), 579 (1), 464 (4) or 47 (3) of the 860 fetch-log grids; the vertices move by up to 3.2–12.2 m.
  [I] So the spike's reprojection made the same per-area choices as PROJ 9.8.1's default, and the choice of
  operation matters. P1-08 should reuse `landslide.sheets.load_sheets` rather than reproject on its own.
  [E] The tightest case is sheet 24-33-01, whose buffered edge sits 0.08 mm from a lattice line; 5 sheets are under
  1 mm. A sub-millimetre change in PROJ or its parameters could move such an edge by one pixel. Downstream tasks
  should read each sheet's grid from the raster itself, not recompute it, and this check should be repeated if the
  PROJ version changes.
- **Deviation?** No.

## D-new-1 · Grid snapping and grid equality

- **Decision.** `snap_out` takes the box (bounds ± 250 m) and returns integer pixel-edge indices on the lattice
  x = 0.4 + 2i, y = −0.12 + 2j: `i0 = floor((xmin − 0.4)/2 + ε)`, `i1 = ceil((xmax − 0.4)/2 − ε)`, likewise for y,
  with ε = 10⁻⁹ cell so a value that is on a lattice line up to float noise stays put. Width = i1 − i0, height =
  j1 − j0. Grids compare as integer tuples (left index, top index, w, h). A fetch-log corner or a raster transform is
  accepted as on-lattice if it is within 10⁻⁶ m of a lattice line; a raster must be north-up with 2 m pixels.
- **Why.** Comparing indices is exact; comparing floats would need a tolerance on every comparison.
- **Alternatives.** Snapping without ε. Identical on the real data, where the smallest distance of a buffered edge to a
  lattice line is 0.08 mm, much more than ε.
- **Evidence.** Unit tests in `tests/test_sheets.py` (containment, minimality, on-lattice inputs, a known sheet).
- **Deviation?** No.

## D-new-2 · The exportImage request

- **Decision.** The request is note 1 exactly: `bbox` (the snapped grid's xmin, ymin, xmax, ymax, shortest decimal
  repr), `bboxSR=5514`, `imageSR=5514`, `size=w,h`, `format=tiff`, `pixelType=F32`,
  `interpolation=RSP_NearestNeighbor`, plus `f=image`, which returns the TIFF itself. Nothing else is sent: no
  `outSR`, `noData`, `mosaicRule`, `renderingRule` or `compression`. The response body is saved unmodified as
  `data/cache/provenance/<sheet>.tif`, with a sidecar `<sheet>.json` (request, time, ETag, size, sha256).
- **Why.** The brief does not name `f`. `f=image` returns the image itself in one request, so the saved file is the
  unmodified response.
- **Alternatives.** `f=json` returns a link to a temporary file on the server, which takes a second request.
- **Deviation?** No.

## D-new-4 · What "georeferencing equal" means

- **Decision.** Equal size, equal affine transform (all six coefficients, exact), equal GeoTIFF ModelTiepoint and
  ModelPixelScale tags, and equal GeoKeys GTModelType, GTRasterType (PixelIsArea), ProjectedCSType and
  ProjLinearUnits. The download's transform must also equal the recipe grid. The tags are read with Pillow, so the
  check does not depend on how GDAL interprets a vendor CRS string.
- **Why.** The download's GeoTIFF declares `ProjectedCSTypeGeoKey = 5514` but also carries an ESRI PE string with
  `X_Scale = −1`, `XY_Plane_Rotation = 90`. GDAL 3.12 reads that file's CRS as a `LOCAL_CS["S-JTSK / Krovak East
  North", … AUTHORITY["EPSG","5514"]]` without the projection parameters, while the package file (re-encoded) carries
  the full EPSG:5514 definition. Both files identify EPSG:5514 through the same GeoKey; the difference is in how the
  CRS is written, not in the grid.
- **Alternatives.** Comparing `rasterio` CRS objects. They differ (`LOCAL_CS` vs full EPSG:5514) for the encoding
  reason above, so that comparison would fail on every sheet without any coordinate being different.
- **Evidence.** [E] 12 of 12 sheets equal on every field above. The download's GDAL CRS string and both files'
  GeoKeys are recorded per sheet in `results/provenance.json` (`georef_download`, `georef_package`). Downstream code
  reads only the package rasters, never these downloads.
- **Deviation?** No. Reported here so the reviewer can disagree.

## D-new-5 · Value comparison

- **Decision.** Package and download are compared as float32 bit patterns (uint32 views), so −0.0 ≠ 0.0 and any ulp
  difference counts. Per sheet:
  - every pixel where the package is not NaN must be bitwise equal (differences are counted with max, mean, median
    absolute size, a histogram and examples);
  - every package NaN must be NoData in the download (NaN, or the nodata tag if any) or outside the closed range
    [−100, 2000] m;
  - conversely, every NoData or out-of-range download pixel must be NaN in the package (the manifest's stated
    change).

  0 m pixels (outside the border) are valid values for this check; the z ≤ 0 rule applies downstream.
- **Why.** BRIEF.md "Provenance check" and note 1; the card asks for counts and magnitudes of any difference.
- **Evidence.** Unit tests in `tests/test_sheets.py`. [E] 81,849,089 of 81,849,089 compared pixels bitwise equal over
  the 12 sheets, including 5,691,630 cells of 0 m on two border sheets; 0 package NaN cells, 0 invalid download
  cells.
- **Deviation?** No.

## D-new-7 · Full downloads of rows 2–4 (written, not run)

- **Decision.** `fetch_register.py` and `fetch_geology.py` page by object id: the sorted ids (`returnIdsOnly`) are
  split into runs of maxRecordCount, each queried as `(<where>) AND objectid >= lo AND objectid <= hi` with Esri JSON
  output in the native SR; the page must return exactly its ids. Pages are saved unmodified, read with GDAL's
  ESRIJSON driver and written as one GeoPackage. `fetch_sheets.py` does the same with `f=geojson`, which the server
  returns in EPSG:4326 without `outSR`; the script checks that the coordinates are lon/lat. Outputs go to
  `data/cache/rebuild/` so they can never overwrite `data/raw_data/`.
- **Why.** BRIEF.md "Rebuildable without the hand-over"; the brief says to run only the count for rows 2–4.
- **Evidence.** [I] Only the count mode was run against the live services. The paging and the Esri JSON → GeoPackage
  conversion are unit-tested with a fake client and a synthetic page.
- **Deviation?** No.

## D-new-8 · Scan of all 860 package rasters

- **Decision.** Besides the grid check, every package raster is read once and its NaN count, 0 m cells, negative
  cells and min/max are compared with the fetch log's `invalid_frac` (read as the NaN fraction), `zmin` and `zmax`
  (compared as float32). A disagreement fails G1.
- **Why.** None of the 12 sampled sheets has a package NaN, so the "every package NaN explained" clause was never
  exercised on real data. The scan shows whether that is true of the whole package or just the sample.
- **Evidence.** [E] 0 NaN cells and 0 negative cells in all 860 package rasters; 96 sheets contain 0 m cells
  (PLAN.md §5: 96 of 860); `invalid_frac`, `zmin` and `zmax` agree with the fetch log for 860 of 860 sheets. So the
  package's NaN rule changed no pixel, and the NaN clause of the DTM check is vacuous for the whole package, not just
  the sample.
- **Deviation?** No; an extra check.

## D-new-9 · No sheet-grid coordinates in the committed results

- **Decision.** `results/provenance.json` carries sheet numbers, grid sizes, pixel offsets and counts, but no
  EPSG:5514 grid coordinates (the bbox of each sampled sheet, mismatch grids) and not the layer extents of rows 3
  and 4. The full record is written to the gitignored `data/cache/provenance/provenance_full.json`, with the
  per-sheet request sidecars beside it. A unit test checks the redaction.
- **Why.** The grids are the sheet bounds plus 250 m, so they derive from row 3, whose licence is not stated.
  PLAN.md §3 rule 3 keeps anything derived from row 3 out of git, apart from sheet numbers and aggregates.
- **Alternatives.** Committing the full record. The grids are also the extents of CC BY DTM rasters, but they
  outline the sheets to within 250 m, so the conservative reading was taken.
- **Deviation?** No.
