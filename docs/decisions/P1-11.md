# P1-11 decisions: stage-1 baselines and classical-ML comparators (CPU)

Code: `src/landslide/baselines.py`, `scripts/run_baselines.py`; tests: `tests/test_baselines.py` (synthetic meta
tables only). This round is code and tests only: `data/dataset/meta.csv` does not exist yet, so no real number exists.
The orchestrator runs the real baselines later (command at the end).

## Dxx-new · The five scorers and their direction

- **Decision.** Five scorers, in this order, all "higher = more landslide-like":

  | Name | `kind` | Score |
  | --- | --- | --- |
  | `slope_only` | baseline | `meta.slope_mean` as it is (patch-mean slope, °) |
  | `susceptibility` | baseline | `meta.susc_mean` as it is (patch-mean class 0/1/2) |
  | `slope_susc_lr` | classical_ml | StandardScaler + LogisticRegression on `slope_mean, slope_std, susc_mean, susc_high_frac`; P(class 1) |
  | `terrain_stats_lr` | classical_ml | StandardScaler + LogisticRegression on the 12 statistics below; P(class 1) |
  | `terrain_stats_gbm` | classical_ml | HistGradientBoostingClassifier on the same 12; P(class 1) |

  The 12 statistics are the `meta.csv` columns `slope_mean, slope_std, slope_p90, lrm_s_std, lrm_l_std,
  curv_prof_std, curv_plan_std, svf_mean, svf_std, detr_std, detr_range_2_98, tri` (Appendix A §10: "slope mean, std
  and p90; LRM std at both scales; curvature stds; SVF mean and std; detrended std and 2–98 % range; TRI"; PLAN.md
  §4.3 names; P1-10 computes them per D19). Only `meta.csv` is read; the patches are not.
- **Why.** Appendix A §10, including its terminology paragraph (`kind` = "baseline" for the unfitted scores,
  "classical_ml" for the fitted ones). The unfitted scores keep their natural sign: steeper and more susceptible
  terrain is the a-priori landslide direction, and the same sign is what P1-12's stage-2 window-mean baselines use.
  The fitted scores are `predict_proba(...)[:, 1]`, checked to be the probability of label 1 (`classes_ == [0, 1]`).
- **Alternatives.** Flipping a sign after seeing an AUC below 0.5 (post hoc; never). Using the logit instead of the
  probability (same ranks, same AUC).
- **Evidence.** [E, synthetic] `test_unfitted_scores_are_the_columns`, `test_lr_matches_a_plain_sklearn_fit` (the
  pipeline equals a hand-standardised `LogisticRegression` to 1e-12).
- **Deviation?** No.

## Dxx-new · Rows: train on the run's train + inner-val, predict exactly the CNN's test rows

- **Decision.** For each run, `landslide.train.select_unit_rows(run, meta, splits)` (P1-06, the function that picks
  the CNN's rows) gives train, inner-val and test rows. A fitted scorer is fitted on train ∪ inner-val and predicts
  the test rows; an unfitted scorer reads its column on the test rows. Background rows are in no (a) or (b) set.
  - **(a):** runs `a_f0 … a_f4` (`splits.n_folds_a` = 5), one fit per fold and scorer; the five out-of-fold
    prediction sets are pooled (each flysch stage-1 patch is predicted once, by the model that did not see its fold).
  - **(b):** run `b`, one fit per scorer.
- **Why.** Appendix A §10: "Fitted baselines train on the same training blocks (train + inner-val) as the CNN";
  "same splits, same test patches". The CNN uses its inner-val blocks only for early stopping; the baselines have no
  early stopping, so those blocks are training data for them, as the method says.
- **Alternatives.** Fitting on train only (wastes the inner-val blocks; not what §10 says); one (a) model on all
  flysch blocks (leaks the test fold).
- **Evidence.** [E, synthetic] `test_fit_rows_are_train_plus_inner_val` (every run); `test_estimators_receive_only_fit_rows`
  (a spy on what each estimator is fitted on, rows identified by their exact feature vectors: equal to train ∪
  inner-val, disjoint from the test rows); `test_test_labels_do_not_influence_their_own_predictions` (flipping the
  labels of a run's test rows leaves that run's predictions bit-identical, while the other (a) folds, which train on
  those rows, change); `test_preds_rows_equal_select_unit_rows` (the ids and folds in `preds_a.csv` / `preds_b.csv`
  are exactly the union of `select_unit_rows(...).test`).
- **Deviation?** No.

## Dxx-new · sklearn settings (fixed, no tuning)

- **Decision.** scikit-learn 1.9.1 (pinned). Every setting is sklearn's default except `random_state`:
  - **StandardScaler:** `with_mean=True, with_std=True` (zero mean, unit variance per feature, from the fit rows
    only; a constant feature is left unscaled by sklearn).
  - **LogisticRegression:** `C=1.0` with `l1_ratio=0.0` (L2 penalty; in 1.9 `penalty` is deprecated and left at its
    sentinel), `solver="lbfgs"`, `max_iter=100`, `tol=1e-4`, `fit_intercept=True`, `class_weight=None`,
    `random_state=replication.seed` (2611).
  - **HistGradientBoostingClassifier:** `loss="log_loss"`, `learning_rate=0.1`, `max_iter=100`,
    `max_leaf_nodes=31`, `max_depth=None`, `min_samples_leaf=20`, `l2_regularization=0.0`, `max_bins=255`,
    `max_features=1.0`, `early_stopping="auto"` (on only above 10,000 training rows, then `validation_fraction=0.1`,
    `n_iter_no_change=10`, `scoring="loss"`, `tol=1e-7`), `class_weight=None`, `random_state=replication.seed`.
  - Every parameter of every estimator (`get_params`) is written to `results/baselines.json` (`scorers.*.settings`)
    and `data/baselines/build_info.json`, so a later sklearn default change would show.
- **Why.** Appendix A §10 and PLAN.md P1-11 ("StandardScaler + LogisticRegression, fixed `random_state`";
  "HistGradientBoosting with defaults and fixed `random_state`"); BRIEF "Fixed settings: no hyperparameter search".
  The task brief asks for `random_state` from `replication.seed`.
- **What `random_state` does here.** Nothing, in practice. lbfgs does not use it (sklearn uses it only for the
  `sag`, `saga` and `liblinear` solvers). HistGradientBoosting uses it for the early-stopping split and for the
  binning subsample above 200,000 rows; with fewer than 10,000 training rows neither happens, and `max_features=1.0`
  draws no features. It is set so that the fits stay reproducible if either condition ever applies.
- **Evidence.** [E] On 4,600 synthetic rows × 12 features: HGB and LR predictions are bit-identical with
  `random_state` 0 and 2611; HGB is bit-identical with 1 thread and with the default 12 (threadpoolctl); LR
  converges in 6 lbfgs iterations; HGB runs all 100 iterations with early stopping off, and switches early stopping
  on at 10,001 rows. [I] The real fit sets are far below 10,000 rows: an (a) fold trains on about 4/5 of roughly
  2,300 flysch pairs (≈ 3,700 rows) and (b) on the Zlínský/Moravskoslezský pairs (≈ 4,000–4,500 rows), so HGB early
  stopping stays off. Each fit records `early_stopping` and `n_iter`, so the real run shows it.
- **Deviation?** No.

## Dxx-new · If logistic regression does not converge

- **Decision.** The fit is kept as it is (no refit with more iterations, no other solver). Every LR fit records
  `converged` (False if sklearn raised a `ConvergenceWarning`), `n_iter` and the warning text, in
  `results/baselines.json` (`fits`, `all_lr_fits_converged`) and `build_info.json`, and the script logs a warning
  naming the run and scorer. The orchestrator then decides, before the freeze, whether to change the rule.
- **Why.** "Defaults, no tuning" fixes `max_iter=100`. A pre-declared fallback (for example `max_iter=10_000` on
  failure) is defensible, because the L2-penalised objective is strictly convex with one optimum, but it is a setting
  that neither the method nor the config names. Recording and reporting is the literal reading and hides nothing.
- **Alternatives.** Refit with a larger `max_iter` (would be the next choice if a real fit fails to converge);
  raise and stop (blocks every other number for a numerical detail).
- **Evidence.** [I] With 4–12 standardised features and thousands of rows, lbfgs typically converges in under 20
  iterations ([E] 6 on the synthetic 4,600 × 12 case above; every synthetic test fit converges in < 100).
  [E] `test_non_convergence_is_recorded_not_hidden` forces `max_iter=1` and checks the record.
- **Deviation?** No.

## Dxx-new · Inputs and missing values

- **Decision.** The scorers read the statistic columns of `meta.csv` (P1-10). A missing column raises `KeyError`; a
  NaN or inf among the rows a run fits on or predicts raises `ValueError` (no imputation). `flysch` is read whether
  the CSV holds `True/False` or `1/0`. If `splits.json` carries a different config hash from the current config, the
  script logs a warning (as `build_samples.py` does).
- **Why.** P1-10 asserts NaN-free patches and computes the statistics from them (D19), so a NaN means a bug upstream
  that must not be papered over. LogisticRegression cannot take NaN; HistGradientBoosting can, but silently, which
  would make the two comparators see different data.
- **Evidence.** [E, synthetic] `test_non_finite_statistic_raises`, `test_flags_read_from_csv_forms`.
- **Deviation?** No.

## Dxx-new · AUC and the two bootstrap CIs

- **Decision.** For every reported subset of a test set: AUC = `metrics.roc_auc` (rank AUC, ties averaged; P1-05).
  Two percentile CIs with `metrics.bootstrap_auc`: one on draws over the subset's **sheets** (primary,
  `eval.bootstrap.unit`), one over its **blocks** (secondary). Both use `eval.bootstrap` n = 2,000, seed 123,
  ci = 0.95, through `metrics.draw_clusters_from_cfg` on the subset's own rows. The draws of a subset are made once
  and shared by the five scorers. Degenerate replicates (one class) are dropped and counted (D21); the counts are in
  the table (`<unit>_n_used`, `<unit>_n_degenerate`). Predictions are fixed; nothing is refitted per replicate.
- **Why.** Appendix A §8 ("sheet-level cluster bootstrap … 2,000 replicates, percentile 95 %, seed 123"; "block-level
  bootstrap CI" secondary); P1-05's note that the block CI uses the same n, ci and seed with the block labels. Since
  `draw_clusters` sorts the cluster labels, P1-13 gets exactly these draws when it draws on the same test rows, so
  CNN − baseline differences can be computed from `preds_*.csv` on the same resamples.
- **Alternatives.** Drawing once over all of a test's sheets and restricting to a subset (the subset's replicate
  sizes would then vary with unrelated sheets, and the per-fold CIs would not match a per-fold computation).
- **Evidence.** [E, synthetic] `test_auc_and_cis_use_the_shared_draws` (every overall AUC equals sklearn's
  `roc_auc_score`; every CI equals `bootstrap_auc` on draws over the same rows); `test_scorer_with_known_auc`
  (hand cases 5/6, 0.75, 1 and 0.5 for a constant score).
- **Deviation?** No.

## Dxx-new · Breakdowns

- **Decision.** `results/baselines.csv` has one row per test × scorer × (breakdown, group):
  - both tests: `overall/all`; `source/<s>` for s in `random, quarry, spoil, rock, cut` ("random" then the config's
    `sampling.lookalike_types`) = **all** of the test's positives against the test negatives of source s (unpaired);
  - (a): `fold/<k>` for k = 0…4, each fold's own test rows (the CNN's per-fold test sets);
  - (b): `kraj/<name>` for every kraj of the (b) test rows (sorted), and `flysch/flysch`, `flysch/nonflysch` by the
    sheet's flysch flag.

  A group without both classes (e.g. a negative source absent from a test set) keeps its row with an empty AUC and
  CIs, its counts, and a `note`.
- **Why.** Appendix A §8 secondary list: per-fold, "(b) by kraj and by flysch flag", "positives against each negative
  source (random vs each look-alike type)". PLAN.md P1-11 item 3. The kraj and flysch breakdowns are asked for (b)
  only (Limitations: "(b) mixes geologies … reported by flysch flag and kraj").
- **Alternatives.** Source breakdown restricted to matched pairs (positive and its own negative only): that is pair
  accuracy, which P1-13 computes for the CNN; Appendix A says "positives against each negative source". Kraj and
  flysch breakdowns for (a) too: (a) is all flysch, mostly Zlínský, and the method does not ask for it.
- **Evidence.** [E, synthetic] `test_breakdown_groups` (group lists, positive and negative counts per source, folds
  and kraje partition the test rows, per-fold AUC = AUC of that fold's rows).
- **Deviation?** No.

## Dxx-new · The matching check

- **Decision.** The slope-only AUC of each test set is the matching check: `results/baselines.json` repeats it under
  `matching_check.a` / `.b` with both CIs, whether the sheet CI contains 0.5, and (a)'s per-fold values. Nothing
  depends on it; it is reported.
- **Why.** Appendix A §8: "Slope-only AUC on each test set as a check that matching worked (≈ 0.5 expected)". Level 5–6
  matches (same stratum, other block) can place a pair in two folds, so per-fold slope AUCs may drift from 0.5 more
  than the pooled one [I].
- **Deviation?** No.

## Dxx-new · Best non-CNN and the spike's reference numbers

- **Decision.** For each test, `results/baselines.json` names the best scorer by point AUC (`best`), and the best of
  each kind (`best_baseline`, `best_classical_ml`). The spike's best non-CNN numbers (BRIEF.md: (a) terrain-stats LR
  0.695 [0.678, 0.713]; (b) terrain-stats GBM 0.624 [0.603, 0.647]) are stored as reference only: in the JSON
  (`spike_reference`, with our AUC of the same scorer and whether it lies inside the spike's CI) and in the CSV columns
  `spike_auc`, `spike_ci_low`, `spike_ci_high`, filled only on the two matching overall rows. They feed no
  computation.
- **Why.** PLAN.md P1-11: "Report the numbers next to the spike's best non-CNN (0.695 / 0.624) without acting on
  them"; BRIEF "Report every number next to the spike's claim"; "a discrepancy does not change the verdict".
- **Deviation?** No.

## Dxx-new · Output files (the interface for P1-13)

- **Decision.**
  - `data/baselines/preds_a.csv`: `id, fold, slope_only, susceptibility, slope_susc_lr, terrain_stats_lr,
    terrain_stats_gbm`; one row per (a) test patch (every non-background flysch stage-1 patch), `fold` = the k of the
    run `a_f<k>` that predicted it (= `meta.fold`), rows in `meta.csv` order.
  - `data/baselines/preds_b.csv`: `id` and the five scorer columns; one row per (b) test patch, in `meta.csv` order.
  - `data/baselines/build_info.json`: `config_hash`, `git_commit`, `git_dirty`, `created`, the sha256 and row count
    of `meta.csv` and `splits.json` and of both prediction files, `splits.json`'s own config hash, the columns, the
    score direction, every estimator setting, every fit record, the determinism check, library versions.
  - `results/baselines.csv` (tracked): columns `test, baseline, kind, breakdown, group, n, n_pos, n_neg, n_sheets,
    n_blocks, auc`, then `sheet_ci_low, sheet_ci_high, sheet_n_used, sheet_n_degenerate`, the same four for `block`,
    then `spike_auc, spike_ci_low, spike_ci_high, note`. Full float precision.
  - `results/baselines.json` (tracked): `task, config_hash, git_commit, inputs` (hashes and counts), `outputs`,
    `bootstrap, random_state, scorers` (kind, model, features, settings), `tests.{a,b}` (definition, runs, counts,
    counts by source, overall results per scorer with both CIs, best, best per kind, (a) per-fold AUCs, the spike
    reference), `matching_check, fits, all_lr_fits_converged, spike_reference`. No timestamps, so a rerun on the same
    inputs and commit gives the same file.
  - `--out DIR` redirects everything (including the log) under DIR, for checks and tests. Files are written to a
    temporary name and renamed.
- **Why.** The task brief fixes the prediction files' names and columns now, for P1-13. Sheet numbers, kraj names
  and aggregate AUCs only appear in tracked files (BRIEF "Constraints": aggregate results are fine); no coordinates.
- **Evidence.** [E, synthetic] `test_script_outputs_and_schema` runs the script end to end into a temporary
  directory and checks every file, column, kind, the absence of duplicate groups, the config hash and that nothing
  is written elsewhere.
- **Deviation?** No.

## Dxx-new · Determinism

- **Decision.** No step draws random numbers except the bootstrap (seed 123, via P1-05). The fits are deterministic
  (see the settings section). `--check-determinism` computes everything twice in one process and writes nothing
  unless the prediction files, the table and the JSON summary are identical.
- **Evidence.** [E, synthetic] `test_determinism` (two runs identical; shuffling the rows of `meta` leaves every
  patch's unfitted scores identical and its fitted scores equal to 1e-9; the summation order of the scaler and the
  solver can move the last bits); the script test runs with `--check-determinism`.
- **Deviation?** No.

## Dnew-config · Values without a config key (requests, none required)

- **Scorer definitions.** Module default `landslide.baselines.DEFAULT_SPECS` (Appendix A §10). If the config gains
  `replication.baselines.scorers` (a list of `{"name", "model": "column" | "lr" | "gbm", "features": [...]}`), it is
  used instead and validated. **Optional request to P1-16:** add it so the frozen config records the five scorers:

  ```json
  "baselines": {"scorers": [
    {"name": "slope_only", "model": "column", "features": ["slope_mean"]},
    {"name": "susceptibility", "model": "column", "features": ["susc_mean"]},
    {"name": "slope_susc_lr", "model": "lr", "features": ["slope_mean", "slope_std", "susc_mean", "susc_high_frac"]},
    {"name": "terrain_stats_lr", "model": "lr", "features": ["slope_mean", "slope_std", "slope_p90", "lrm_s_std",
      "lrm_l_std", "curv_prof_std", "curv_plan_std", "svf_mean", "svf_std", "detr_std", "detr_range_2_98", "tri"]},
    {"name": "terrain_stats_gbm", "model": "gbm", "features": ["...the same 12..."]}]}
  ```
- **Secondary bootstrap unit.** `eval.bootstrap.secondary_unit` if present, else "block" (P1-05's suggestion for
  P1-16).
- **Negative sources** come from `sampling.lookalike_types` (plus "random"); **random_state** from
  `replication.seed`; **bootstrap** n, seed, ci from `eval.bootstrap`; **folds** from `splits.n_folds_a`.
- The spike's reference numbers are claims from the brief, kept in `SPIKE_BEST_NON_CNN`, not config values.

## Running it (for the orchestrator)

- After P1-10 has written `data/dataset/meta.csv`, from the main checkout:

  ```powershell
  uv run python scripts/run_baselines.py --check-determinism
  ```

  It reads only `meta.csv` and `splits.json`, runs on the CPU in about a minute [I], and writes the five files above.
  From a worktree, set `LANDSLIDE_DATA_DIR` to the main checkout's `data` first (then the tracked results land in the
  worktree's `results/`).
- **Config hash.** `build_info.json` and `results/baselines.json` carry the hash of the config they ran with. If
  P1-16 changes the config (for example the keys requested above or by other tasks), the hash changes, so the
  baselines should be (re)run after the freeze for the hashes to match the frozen one. The rerun is cheap and
  deterministic.
