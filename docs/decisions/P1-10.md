(the D19 statistics), `scripts/build_patches.py`, `scripts/verify_dataset.py`. Tests: `tests/test_features.py`
(brute-force formulas), `tests/test_patches.py` with `tests/patches_synth.py` (P1-09's synthetic world, its rasters
written as GeoTIFFs in a `data/` layout).

## D19 · Patch statistics

- **Decision.** `features.patch_stats` computes the 14 `meta.csv` statistics in float64 over the 150 × 150 patch
  (never the 28 px context), from the float64 output of `channels.patch_channels`, before the cast to float16:
  - means with `ndarray.mean`; standard deviations are population std (ddof = 0, `ndarray.std`);
  - `slope_p90` = `np.percentile(slope, 90)` and `detr_range_2_98` = `percentile(detr, 98) − percentile(detr, 2)`,
    both with numpy's default linear interpolation (the same rule P1-09 used for the cut p90);
  - `slope_mean, slope_std, slope_p90` of slope; `lrm_s_std`, `lrm_l_std`, `curv_prof_std`, `curv_plan_std` of
    their channels; `svf_mean, svf_std`; `detr_std`, `detr_range_2_98` of detr (the patch's own plane residual);
    `tri` (D19a-new); `susc_mean`, `susc_high_frac` (D19b-new).
  - Channels are looked up by name (`cfg["channels"]`), not by position.
- **Why.** PLAN.md D19 ("over the 150 × 150 patch (not the context), from float64 channels"); Appendix A §10 lists the
  12 terrain statistics and the slope_susc_lr inputs.
- **Alternatives.** Sample std (ddof = 1): a constant factor √(22500/22499) on every patch, irrelevant to any AUC;
  ddof = 0 is numpy's default. Statistics from the float16 patches: rejected by D19.
- **Evidence.** [E, synthetic] `test_stats_against_brute_force`: every statistic equals a written-out formula
  (`math.fsum` means and stds, closest-rank linear interpolation) to 1e-12 on random patches;
  `test_channel_order_follows_names`. `test_patches_equal_the_channels_of_the_sampled_dtm`: every `meta.csv`
  statistic equals `patch_stats` on the in-memory synthetic DTM exactly.
- **Deviation?** No.

## D19a-new · TRI

- **Decision.** TRI = the mean over the 150 × 150 patch pixels of each pixel's mean absolute elevation difference to
  its 8 neighbours, on the DTM z (unsmoothed, metres). The patch-edge pixels' neighbours lie one pixel into the
  context, so the statistic reads the patch plus a 1 px ring (`extract_block(z, r − 76, c − 76, r + 76, c + 76)`),
  exactly as slope's central differences do at the patch edge.
- **Why.** PLAN.md D19 states the formula explicitly ("mean over the patch of the mean |z − 8 neighbours|").
- **Naming (flagged, not acted on).** D19 calls this formula "Riley". Riley et al. (1999) defined TRI as
  √(Σ (z_n − z)²) over the 8 neighbours; the mean absolute difference is the variant GDAL calls "Wilson". We follow
  D19's explicit formula and record the mismatch for the orchestrator. Both are monotone measures of local relief and
  feed only the terrain-stats comparators.
- **Alternatives.** Riley's root-sum-of-squares; computing over the 148 × 148 interior only. Not chosen: the formula
  is given, and using the context ring keeps every patch pixel, as for the other per-pixel channels.
- **Evidence.** [E, synthetic] `test_tri_brute_force_and_plane`: equals a pixel loop to 1e-13; on a plane z = a·col +
  b·row it equals (|a| + |b| + |a + b| + |a − b|) / 4 exactly; 0 on a constant surface; NaN propagates.
  `test_tri_uses_the_ring`: changing only a ring cell changes the TRI by the expected amount.
- **Deviation?** No.

## D19b-new · Susceptibility statistics

- **Decision.** From P1-07's class raster (`Paths().susceptibility(sheet)`, uint8 on the sheet's DTM grid: 0 low or
  no data, 1 mid, 2 high), over the same 150 × 150 pixels as the patch: `susc_mean` = mean class code,
  `susc_high_frac` = fraction of code-2 pixels. A code outside {0, 1, 2} stops the build. The class raster must be on
  the sheet's grid (lattice origin and size equal to `sheets.parquet`'s, checked per sheet).
- **Why.** PLAN.md D19 ("Susceptibility stats over the patch footprint"); Appendix A §9-§10 (window-mean class and
  high-class fraction).
- **Licence.** Row 5 has no stated licence. Its numbers appear only as these per-patch columns of `meta.csv` inside
  `data/`; `results/dataset_summary.json` and the figure carry nothing derived from it (tested: no "susc" in the
  summary).
- **Evidence.** [E, synthetic] `test_susceptibility_stats` (hand counts; code 3 raises);
  `test_window_outside_the_raster_and_misaligned_grids` (a class raster shifted by one pixel is refused). [E, real,
  read-only benchmark] On 6 real sheets the class rasters were accepted on the DTM grid and gave codes in {0, 1, 2}.
- **Deviation?** No.

## D19c-new · `slope_mean` and `slope_bin` in `meta.csv`

- **Decision.** `slope_bin` is P1-09's stored bin (never recomputed). `slope_mean` in `meta.csv` is also P1-09's
  stored value, the one matching used. The mean recomputed from the float64 patch must equal it within 1e-9°; the
  build stops at the first sample that does not (`SLOPE_MEAN_TOL`, checked per sample, so a failure comes early). The
  number of bins that would flip if recomputed is counted in `build_info.json`
  (`slope_bin_flips_recomputed_vs_stored`), not failed.
- **Why.** P1-09 Dnew-samples ("Use the stored `slope_bin`"). Keeping the stored mean keeps `slope_mean` and
  `slope_bin` consistent and equal to what the matching saw; the two means come from bitwise-identical slope values
  (P1-04 D18c) and differ only by summation order (SAT vs direct, ~1e-12).
- **Alternatives.** Store the recomputed mean: within 1e-9 of the stored one, but it could disagree with `slope_bin`
  at a bin edge.
- **Evidence.** [E, synthetic] max |recomputed − stored| < 1e-9 on every synthetic sample;
  `test_slope_mean_of_patches_equals_the_sampling_sat_mean` (25 corners, SAT of `full_channels` vs `patch_channels`,
  < 1e-9); `test_slope_mean_mismatch_stops_the_build` (+2e-9 raises).
- **Deviation?** No.

## Dnew-extract · Streaming, one read per raster per sheet

- **Decision.** Samples are processed sheet by sheet (sorted). For each sheet, the window holding every patch plus
  its 28 px context (the bounding box of the 206 × 206 boxes) is read once from the DTM with `dtm.read_dtm(window=…)`
  and once from the class raster (rasterio window read). Each patch is then `channels.patch_channels(z_window, r −
  row_off, c − col_off, cfg)`, the stage-2 code path. The window must lie inside the sheet's grid, and the DTM window's
  lattice offset must equal the grid's. Patches of a sheet can run on threads (`--workers`, default 3); the output is
  written by the main thread into `patches.npy` (`numpy.lib.format.open_memmap`, float16, (N, 7, 150, 150)) at row i
  = sample i. Only one sheet's window is in memory at a time.
- **Why.** PLAN.md §3 rule 11 and the task ("open each raster once, extract all its samples"; 16 GB RAM).
  `patch_channels` cuts its own 206 × 206 block, so the result cannot depend on the window it is cut from.
- **Alternatives.** A `read_dtm` window per patch: opens each raster ~15 times per sheet. The whole raster: reads up
  to twice as much. Neither changes a value.
- **Evidence.** [E, synthetic] `test_bounding_window_equals_per_patch_windows` (bitwise-identical float64 channels
  and statistics); `test_each_raster_is_opened_once_per_sheet` (counts `rasterio.open`: 2 per sheet);
  `test_workers_do_not_change_the_result` (1 vs 4 threads bitwise); `test_build_is_deterministic` (two script runs
  give byte-identical `patches.npy`, `meta.csv` and summary).
- **Deviation?** No.

## Dnew-nan · NaN-free at extraction

- **Decision.** Each patch's float64 channels must be finite, or the build stops naming the sheet, sample id and
  channels. The TRI ring must be finite too.
- **Why.** Appendix A §5 "Storage" ("asserted at extraction"); the brief's phase-1 item 3 ("verify that no patch is
  missing or contains NaN").
- **Evidence.** [E, synthetic] `test_nan_in_the_context_stops_the_build` (one NaN 25 px into the context raises).

## Dnew-float16 · The cast

- **Decision.** Before the cast, every float64 value must be finite with |v| ≤ 65504 (float16's largest finite
  value; a larger value would round to 65504 or to inf). The build records each channel's float64 min and max, the
  headroom to 65504 and the largest float16 rounding error per channel in `build_info.json`. The verification is
  stricter on the stored file: max |value| < 65504 (a stored 65504 may be a saturated value), slope in [0, 90]° and
  svf in [0, 1] (a cheap guard against a wrong channel order).
- **Why.** The task: "no float16 overflow (check the float64 range before the cast)". [I] Physical ranges are far
  below the limit: slope ≤ 90, curvatures are asinh-scaled (|v| < ~20), svf in [0, 1], LRM and detr are metres of
  local relief (|v| < a few hundred).
- **Evidence.** [E, synthetic] `test_float16_cast_checks` (65504 passes; 65504.5, 7e4, ±inf, NaN raise);
  `test_float16_overflow_stops_the_build` (a 1e5 m spike raises); `test_extraction_info` (the rounding error is at
  most half a float16 spacing at each channel's largest magnitude).

## Dnew-meta · `meta.csv`

- **Decision.** Columns (`patches.META_COLUMNS`): `id, label, x, y, row, col, sheet, kraj, flysch, source,
  polygon_objectid, source_layer, source_objectid, fold, group_b, block, stratum, slope_bin, match_level, pair_id`,
  then the 14 statistics in PLAN.md §4.3 order. Row i describes `patches[i]` and is `samples.parquet` row i
  (`id` = i). UTF-8, "\n" line ends, floats as their shortest round-trip repr. `landslide.patches.read_meta` reads it
  with fixed dtypes. The build re-reads the file and asserts every value is bit-identical.
- **Why.** PLAN.md §4.3. `source_layer` and `source_objectid` are P1-09's additions (P1-09 Dnew-samples); they go
  after `polygon_objectid`, as in `samples.parquet`.
- **Note.** pandas 3.1 deprecates `read_csv(float_precision=…)`. [E] Its default parser read 300,000 random
  shortest-repr floats (magnitudes 1e-12 … 1e8, plus edge values) back exactly, so `read_meta` uses the default, and
  the build's round-trip assertion guards it.
- **Contract.** The two extra columns are an addition to PLAN.md §4.3 (already flagged by P1-09); this task does
  not edit PLAN.md.
- **Evidence.** [E, synthetic] `test_meta_columns_order_and_roundtrip`.

## Dnew-summary · `results/dataset_summary.json`

- **Decision.** Aggregate counts only: `n_patches`, the shape and channel order, then by label, kind (positive /
  matched negative / background), source, kraj, flysch flag, fold, `group_b` and stratum (each split into positive,
  negative, background, total), by match level (negatives) and match level × source. It also has the matched counts
  of each test set: (a) `fold ≥ 0`, (b) test `group_b == "test"`, (b) train. Pair numbers: same sheet, same bin, and
  the median, p90 and max of |Δ slope_mean|. Plus `config_hash` and `git_commit`. No coordinates, no per-sheet
  numbers, nothing from the susceptibility map.
- **Why.** PLAN.md P1-10 card item 3 and the brief's phase-1 report (counts by label, source, kraj, flysch flag and
  fold). The background sample (`pair_id` −1) is in no test set (Appendix A §5: stage-2 model and secondary reference
  only).
- **Evidence.** [E, synthetic] `test_summary_counts_and_contents` (counts add up; no "x", "row", "geometry",
  "grid_", "susc" or sheet number in the text).

## Dnew-figure · `figures/slope_distributions.png`

- **Decision.** Two panels: (a) the flysch folds pooled and (b) the transfer test group, matched patches only.
  Each panel is a histogram of patch-mean slope in the 2° matching bins (`slope_bin_deg`), with positives (blue) and
  their negatives (orange) as side-by-side bars in each bin, n in the legend. Histograms only: no maps, no
  susceptibility. Colours are slots 1 and 2 of the dataviz reference palette. The grid is recessive and the PNG is
  light mode only.
- **Why.** P1-10 card item 4; BRIEF.md "Constraints" (no maps of rows 3–5, no sheet outlines). Side-by-side bars
  stay legible where the two counts are equal, which exact-bin matching makes common; overlaid outlines would hide
  one class.
- **Evidence.** [E, synthetic] `test_figure_is_written`. The layout was checked by eye at the real scale (3,500
  fabricated pairs, scratchpad only).

## Dnew-verify · `scripts/verify_dataset.py`

- **Decision.** Every check runs and is reported (PASS/FAIL/WARN); the script exits 1 on any FAIL.
  - `files`, `shape_dtype` (float16, C order, (len(meta), 7, 150, 150)) and `file_size` (exactly header + data, and
    as in `build_info.json`).
  - `nan_inf`, `float16_overflow`, `channel_bounds` (a full chunked scan of the file).
  - `meta_columns` (exact order, finite statistics) and `unique_ids` (id = row number).
  - `labels_sources` (label 1 ⇔ positive; pair_id −1 ⇔ background; match_level 0 / 1–6).
  - `pairs`: each pair_id has exactly one positive and one negative, same stratum, and the slope-bin rule of its
    match level.
  - `meta_vs_samples`: every sample column equals `samples.parquet` row by row.
  - `patch_rule`, rechecked from the coordinates: x, y are exactly the corners (row, col) of the sheet grid; the
    patch plus context lies inside the raster; the 300 m square is `covered_by` its own stage-1 sheet; and no
    stage-2 sheet lies within 150 m (`dwithin`, exact geometry; the 150 m comes from `sampling_params`).
  - `alignment`: a seeded sample of rows plus the first and last row is re-extracted, each with its own
    `read_dtm` window (patch plus 28 px context, the path the build does not use). The float16 patch must be
    bit-identical to `patches[i]`, and the statistics equal to `meta.csv` (slope_mean 1e-9 abs, others 1e-9
    relative).
  - `build_info` (must exist; sha256 of `meta.csv` and `patches.npy` as recorded; `--no-hash` skips the 3.5 GB
    hash) and `summary` (row count and config hash agree).
  - `config_hash`: a mismatch with the current config is a WARN, not a FAIL. The freeze (P1-16) may add config keys,
    which changes the hash without changing any extraction value; whether to rebuild then is the orchestrator's
    call.
- **Seeded rows.** 200 by default (`--n-check`), drawn without replacement from
  `SeedSequence([replication.seed, stream])` with the stream `verify_sample` (D02). That stream is not registered in
  the config yet; until it is, id 11 is used (the next free id; the code refuses it if 11 is ever taken by another
  stream).
- **Why.** P1-10 card item 5. Bitwise equality is possible because extraction is deterministic and the 206 × 206
  block is identical whichever window it is cut from (Dnew-extract).
- **Evidence.** [E, synthetic] `test_verify_passes_on_the_build` (all 16 checks pass, every row re-extracted); each
  failure mode is caught by the intended check: swapped patches and swapped meta rows (`alignment`), NaN / −inf
  (`nan_inf`), a stored 65504 (`float16_overflow`), slope 91° and svf −0.01 (`channel_bounds`), a duplicate id
  (`unique_ids`), a second negative in a pair (`pairs`), a meta column out of step (`meta_vs_samples`), x off the
  corner and a square leaving its sheet (`patch_rule`), a truncated file (`file_size`), a float32 file
  (`shape_dtype`), a missing `build_info.json` (`build_info`); a config-hash mismatch only warns;
  `test_verify_script_exit_codes` (0 on the build, 1 after one NaN).

## Dnew-build-info · `data/dataset/build_info.json` and atomic outputs

- **Decision.** The build deletes any old `build_info.json` first and writes it last. It records the config hash, git
  commit, time, the `samples.parquet` sha256 and rows, the `patches.npy` shape, dtype, header size, bytes and sha256,
  the `meta.csv` rows, columns, bytes and sha256, the extraction numbers (channel ranges, float16 error, the slope-mean
  check) and timings. `patches.npy` is written as `patches.npy.part` and renamed when complete. If the extraction
  fails, the partial file is deleted (the traceback's frames are cleared first, because Windows locks a mapped
  file). `meta.csv` and the JSON files are also written to `.part` files and renamed.
- **Why.** A stopped build must not look finished. The verification requires `build_info.json` and its hashes.
- **Evidence.** [E, synthetic] `test_build_info`; `test_failed_build_leaves_no_partial_files`.

## Dnew-config · Values without a config key (requests)

- **`replication.streams.verify_sample`: 11** (requested, for P1-16). It is the verification's seeded row sample. The
  code reads it from the config if present, otherwise uses 11.
- Not config values (no request): the check tolerances `SLOPE_MEAN_TOL` = 1e-9° (the task's tolerance) and
  `STAT_RTOL` = 1e-9; the float16 maximum (numpy); the physical bounds of slope and svf; the figure colours; the
  number of verification rows (a CLI option). The context (28 px), patch size, channel order, slope bin and the
  150 m stage-2 buffer come from existing keys through `channel_params` and `sampling_params`.

## Build time and disk (estimates for ~11,200 patches)

- **Time.** [E, real, read-only] Benchmark on 6 random stage-1 sheets, 15 random fully valid corners each (the expected
  density, 11,200 / ~750 sheets): reading the bounding windows 0.24 s per sheet; extraction with statistics and the
  cast 39 ms per patch on 1 thread and 31 ms on 3 threads (the default). [I] So about 9–10 min for 751 sheets and
  11,200 patches, plus ~15 s to hash the files. The verification takes about 1 min: [E] a full scan runs at about
  0.35 GB/s and sha256 at about 0.8 GB/s (1 GB dummy file), plus about 200 re-extractions.
- **Disk.** 11,200 × 7 × 150 × 150 × 2 B = 3.53 GB (3.28 GiB) for `patches.npy` plus a 128-byte header, and about
  5 MB for `meta.csv`. The patch file is written in place as `.part` (no second copy). The build refuses to start
  with less than the file size + 1 GB free; [E] 100 GB was free on C: on 2026-11-26.
- **Memory.** One sheet window (≤ 2,900 × 2,900 float64 ≈ 65 MB, plus the uint8 class window) and a few MB per
  thread; the patch file is memory-mapped.
