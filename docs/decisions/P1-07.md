# P1-07 decisions: susceptibility (row 5), ZABAGED (row 6) and the ImageNet weights (row 8)

Results: `results/sources.json` (aggregate numbers only). Code: `src/landslide/susceptibility.py`,
`scripts/fetch_susceptibility.py`, `scripts/fetch_zabaged.py`, `scripts/fetch_weights.py`. Data (gitignored):
`data/cache/susceptibility/`, `data/cache/zabaged/`, `data/cache/torch/`.

## D-new-1 · The susceptibility request (row 5)

- **Decision.** One `MapServer/export` request per sheet and class, exactly BRIEF.md note 5: `bbox` and `size` of the
  sheet's package DTM raster, `bboxSR=5514`, `imageSR=5514`, `format=png32`, `transparent=true`, `layers=show:0`,
  `dpi=96`, and `layerDefs={"0": "struktura LIKE 'Třída střední%'"}` (mid) or `'Třída vysoké%'` (high). Added:
  `f=image`, which returns the PNG itself (the brief does not name `f`; the ArcGIS default is an HTML page). The bbox
  is written like the DTM recipe's (shortest decimal repr of each edge). The `layerDefs` JSON is sent as UTF-8 and
  percent-encoded by `requests`. No `outSR`. All requests go through `landslide.net.Client`.
- **Grid.** Each sheet's grid is read from its package raster in `data/raw_data/dmr5g/` (transform and size, checked
  to lie on the native lattice with `sheets.grid_from_transform`), never recomputed (P1-03 D03). The class raster
  copies that raster's transform, size and CRS.
- **Why.** BRIEF.md note 5; P1-03's finding that grids should be read from the rasters.
- **Evidence.** [E] The server's own description of each render (`f=json`, same parameters) gives exactly the
  requested extent (difference 0.0 m on all four edges), the requested size and scale 7559.04 (= 2 m pixels at
  96 dpi; float noise in the last digits), in wkid 102067 / latest 5514: 4 of 4 renders on the two sheets inspected
  before the run, 78 of 78 on the 39 sheets inspected in all (D-new-6). [E] All 1,720 PNGs of the full run have their
  DTM raster's size (asserted per request; a mismatch would have stopped the run). [E] A header check of all 860 class
  rasters afterwards: transform, size and CRS equal to the DTM raster's, uint8, deflate, codes 0–2 only.
- **Deviation?** No.

## D-new-2 · PNG → class (alpha ≥ 128)

- **Decision.** The PNG must be an RGBA PNG of the requested size. A pixel belongs to the rendered class if its alpha
  is ≥ 128 (note 5). The RGB of every class pixel must be the class's symbol colour from the layer's renderer (mid
  255,255,0; high 255,0,0); any other colour stops the run.
- **Why.** Note 5 fixes the threshold. The colour check catches a render that ignored `layerDefs` (e.g. drawn from
  the service's tile cache with every class) or a symbology change, either of which would silently corrupt the
  classes.
- **Evidence.** [E] The renders are not binary: alpha takes the values 0, 64, 128, 191 and 255 (4-sample coverage at
  polygon edges), although the service's `documentInfo` says `AntialiasingMode: None`. So alpha ≥ 128 means "at least
  half the pixel covered". Over all 860 sheets, 2.2 % of the pixels with any mid alpha and 5.3 % of those with any
  high alpha are partial (64, 128 or 191); totals in `results/sources.json` (`renders.alpha_histogram`).
  [E] 0 class pixels of an unexpected colour in the whole run.
- **Deviation?** No.

## D-new-3 · Pixels in both the mid and the high render

- **Decision.** Such a pixel gets code 2 (the higher class wins). The pixels are counted per sheet, with a histogram of
  their (mid alpha, high alpha) pairs.
- **Why.** The brief defines the codes (0 low/no data, 1 mid, 2 high) but not overlaps. Two causes occur: (a) with
  antialiased edges, a pixel cut half-and-half by a mid/high boundary has alpha 128 in both renders and passes both
  thresholds; (b) in a few places the mid and high polygons of the source layer themselves overlap. Taking the higher
  class is the ordinal maximum, and for (b) it is the stricter reading of a map that marks the spot as high.
- **Alternatives.** Mid wins; the larger alpha wins (no help for the 128/128 and 255/255 pairs, which are 95 % of the
  overlap); leaving such pixels at 0. Each changes only the overlap pixels, 0.014 % of all pixels.
- **Evidence.** [E] 816,949 overlap pixels in 277 of 860 sheets, 0.014 % of the 5,819,646,142 rasterised pixels.
  (mid alpha, high alpha): (128, 128) 692,681 (84.8 %, boundary ties); (255, 255) 83,547 (10.2 %, overlapping
  polygons); other combinations of 128/191/255 40,721 (5.0 %). [E] Point queries at 27 pixels with alpha 255 in both
  renders (3 sheets with the most such pixels, plus the sample of D-new-6): the vector layer returns both a mid and a
  high polygon at all 27, so the overlap is in the source data, not a rendering artefact.
- **Deviation?** No; it settles a case the brief leaves open.

## D-new-4 · What is kept, and the resumable log

- **Decision.** Per sheet: `data/cache/susceptibility/<sheet>.tif` (uint8, deflate, tiled 256, no NoData value, tags
  CLASSES/SOURCE/RECIPE/RETRIEVED_UTC/SHEET), the two unmodified PNGs in `png/`, and one line in `fetch_log.jsonl`
  (request parameters, time, sha256 and size of each PNG, alpha histograms, colour checks, class and overlap
  counts). A sheet with a log line and a raster is skipped on a re-run. Each invocation appends to `runs.jsonl`
  (time, status, request count). The run stops at the first error after the client's retries.
- **Why.** The card asks for a resumable run with a jsonl log; keeping the PNGs lets the class rule be re-applied
  offline. Stopping (rather than skipping a sheet) follows the task rule "stop and report rather than work around".
- **Evidence.** [E] 860 of 860 sheets: 860 class rasters (67.0 MB) and 1,720 PNGs (214.5 MB). Pixel-weighted over
  all rasters: low or no data 77.2 %, mid 10.4 %, high 12.5 %; 105 sheets have no mid or high pixel (aggregates in
  `results/sources.json`).

## D-new-5 · Service checks before rendering

- **Decision.** Before any render: the service and layer descriptions are read and recorded; each LIKE pattern must
  select exactly one distinct `struktura` value (a group-by count query); each class must have one renderer colour;
  the largest DTM grid must fit the service's image limit; the service SR must be EPSG:5514; png32 must be supported.
- **Evidence.** [E] Service version 10.91 (document `sesuvy_mapa_all_v93`), image limit 4096 × 4096 (largest grid
  2902 × 2496), SR wkid 102067 / latest 5514. Three distinct classes: high 603,545 features, mid 212,883, low
  372,528; each pattern selects exactly one. Layer 0 has no scale range (minScale = maxScale = 0).

## D-new-6 · Inspection before the full run, and a sample after it

- **Decision.** Two sheets were rendered and inspected before the full run: 25-14-17 (flysch) and 04-33-10 (a border
  sheet, partly abroad). For each: the `f=json` extent check (D-new-1), then point queries of the vector layer
  (`query`, point geometry in EPSG:5514, `returnGeometry=false`) at pixel centres chosen deterministically (evenly
  spaced over the raster order, no RNG) in seven categories: fully covered pixels deep inside a mid / high / neither
  area (5 × 5 window uniform), the first fully covered pixel at an edge (a 4-neighbour has alpha < 255) of each, and
  (added after the full run showed 255/255 overlaps) pixels fully covered in both renders. A render shifted by a pixel
  would fail many edge points. A point's service class is the highest class among the polygons containing it.
  After the full run the check was repeated, 3 points per category, on 37 more sheets chosen by a fixed rule: 15
  evenly spaced over the sorted list of the 105 sheets with no mid or high pixel (a blank render could also be a
  server-side drawing failure), every 43rd sheet of the sorted 860 from index 21 (20), and the 3 sheets with the most
  255/255 overlap pixels.
- **Evidence.** [E] Before the run: 70 of 70 points agree (mid 20, high 20, neither 30), and 4 of 4 extents.
  04-33-10 has no mid or high pixel; its points return the low class (8) or no polygon (2, abroad), so its empty
  renders are real. On 25-14-17 the mid share is 2.7 % and high 9.6 %. A plausibility check: mean slope is 8.8° in
  class 0, 17.1° in class 1 and 17.1° in class 2. [E] After the run, all 39 inspected sheets together: 475 of 475
  points agree (mid 128, high 116, neither 204, both 27) and 78 of 78 extents. On the 15 all-low sheets every point
  returns the low class (37) or no polygon (8, abroad), so those blank renders are real.
- **Licence.** The per-point record (with coordinates) is `data/cache/susceptibility/inspection.json`; only the
  agreement counts go to `results/sources.json`.

## D-new-7 · ZABAGED envelope queries (row 6)

- **Decision.** For each layer (118, 119, 130, 129, 79, 75) and each of the 860 sheets: an envelope query with the
  bbox of the sheet's package DTM raster (`geometryType=esriGeometryEnvelope`, `inSR=5514`,
  `spatialRel=esriSpatialRelIntersects`, no `outSR`). Paging reuses P1-03's `sheets.query_pages` through a small
  adapter (`EnvelopeClient`) that adds the envelope to every request: `returnIdsOnly` gives the envelope's object
  ids, then pages of at most maxRecordCount (2,000) consecutive ids are queried as
  `(1=1) AND OBJECTID >= lo AND OBJECTID <= hi` plus the same envelope, `outFields=*`, `orderByFields=OBJECTID`,
  `f=json` (Esri JSON in the native SR). Each page must return exactly its ids, and `exceededTransferLimit` must be
  absent. Each response page is saved unmodified under `data/cache/zabaged/pages/<layer>/<sheet>/`, and each finished
  (layer, sheet) is appended to `fetch_log.jsonl` (resumable; stops at the first error).
- **Why.** The task's recipe; id paging with an exact-ids check is complete by construction, unlike offset paging.
  The envelope is the DTM grid (sheet + 250 m), which also covers P1-09's 150 m exclusion around ZABAGED
  landslide/scree: any feature within 150 m of a point inside the sheet intersects the envelope. Features are
  returned whole (not clipped), so road and rail lines keep their full length.
- **Alternatives.** Offset paging (`resultOffset`), or keyset paging on the feature query alone: one request fewer
  per (layer, sheet) but completeness rests on `exceededTransferLimit`.
- **Evidence.** [E] Layer metadata (read first, recorded): all six are in wkid 102067 / latest 5514, maxRecordCount
  2,000, object-id field `OBJECTID`, service version 11.5. Live geometry types: 118, 119, 130 and 129 are
  `esriGeometryPolygon`, 79 and 75 `esriGeometryPolyline`. So layer 130 holds polygons, not points (PLAN.md D15
  anticipated points). National feature counts: 118 641, 119 186, 130 39,444, 129 478, 79 41,363, 75 5,245.
- **Deviation?** No.

## D-new-8 · Local conversion, deduplication and the GeoPackages

- **Decision.** The saved pages are read with GDAL's ESRIJSON driver (`sheets.esri_pages_to_frame`, which checks
  that each page declares wkid 102067 / latest 5514 and labels it EPSG:5514 without changing a coordinate). Rows are
  deduplicated by `OBJECTID`; rows that share an id must be identical in every attribute and in their geometry WKB,
  otherwise the build stops. One GeoPackage per layer, named by the layer id: `data/cache/zabaged/<id>.gpkg`
  (`Paths().zabaged("118")`, layer `zabaged_<id>`), all attributes as served, sorted by `OBJECTID`. Geometries are
  written unchanged (`promote_to_multi=False`: pyogrio would otherwise turn a Polygon/MultiPolygon mix into
  MultiPolygon for GPKG), and the file must read back with identical ids and WKB.
- **Why.** A feature near a sheet edge, or a long road, is returned for several sheets. Naming by layer id follows the
  brief, which identifies the layers by number.
- **Evidence.** [E] 5,148 (layer, sheet) envelope queries, all complete; 0 duplicate ids with differing content;
  0 null, empty or invalid geometries; every GeoPackage reads back with identical ids and WKB; `fid_zbg` (ZABAGED's
  own id) is unique in every layer.

  Saved pages: 2,068 files, 107 MB.
- **Deviation?** No.

## D-new-9 · ImageNet weights (row 8)

- **Decision.** `TORCH_HOME` is set to `Paths().torch_home` (`data/cache/torch`) before torch is imported, and the
  weights the config names (`model.init` → `ResNet18_Weights.IMAGENET1K_V1`) are fetched with torchvision's own
  `WeightsEnum.get_state_dict(check_hash=True)`, which checks the sha256 prefix in the file name. The file must be
  `landslide.model.imagenet_weights_path(cfg, paths)`. The offline check runs in a fresh Python process that first
  replaces `socket.socket.connect`, `connect_ex`, `socket.create_connection` and `socket.getaddrinfo` with a function
  that raises, verifies that a real HTTPS request now fails, and only then imports torch and calls
  `landslide.model.build_model(cfg, path)` and a forward pass.
- **Evidence.** [E] `data/cache/torch/hub/checkpoints/resnet18-f37072fd.pth`, 46,830,571 bytes, sha256
  `f37072fd47e89c5e827621c5baffa7500819f7896bbacec160b1a16c560e07ec` (prefix matches the file name), torch
  2.14.1+cu130, torchvision 0.29.1+cu130. Offline: network blocked (verified), 102 tensors loaded strictly, every
  backbone tensor equal to the file's, conv1 (64, 7, 7, 7) equal to the mean-RGB formula, output (2, 1) finite.
- **Deviation?** No.

## D-new-10 · Request etiquette and parallel runs

- **Decision.** Every row-5 and row-6 request goes through `landslide.net.Client` (allowlist, User-Agent, ≥ 0.3 s
  between requests, retries with backoff on 429/5xx). The susceptibility and ZABAGED runs ran at the same time,
  each with its own client, against different hosts (`mapy.geology.cz`, `ags.cuzk.gov.cz`), so each service still saw
  one request at a time with ≥ 0.3 s gaps.
- **Evidence.** [E] Before writing the scripts, 15 exploratory requests read service and layer metadata and rendered
  one sheet (8 to `mapy.geology.cz`, 7 to `ags.cuzk.gov.cz`); nothing from them is used in any output. Script
  requests (`results/sources.json`, `runs`): susceptibility 2,282 (81 for the first two sheets and their inspection,
  1,719 for the other 858 sheets, 482 for the post-run inspection); ZABAGED 7,260 (35 for a two-sheet trial, 7,225
  for the rest); weights 1 download from `download.pytorch.org`. No HTTP error reached the scripts (the client's
  silent retries are not counted), no size mismatch, no empty layer. Wall time: 52 min for the 858 susceptibility
  renders and 44 min for the ZABAGED queries, run side by side.

## D-new-11 · Licence handling of the outputs

- **Decision.** Row 5 has no stated licence: the class rasters, the PNGs, the per-sheet log and the inspection points
  stay under `data/`. `results/sources.json` carries only aggregates (pixel-weighted class fractions, quantiles of the
  per-sheet fractions, counts) and sheet numbers; the service metadata is recorded without the layer extent (as
  P1-03 did for rows 3 and 4). ZABAGED (CC BY 4.0, © ČÚZK) stays in `data/` as data; its layer metadata, extents
  included, is in `results/sources.json`.

## D-new-12 · Values that are not config keys

- **Decision.** The row-5 service URL, layer id, class field and LIKE patterns, the alpha threshold (128), `dpi` and
  `format` are module constants in `landslide.susceptibility` (BRIEF.md note 5). The row-6 service URL and layer ids
  are constants in `scripts/fetch_zabaged.py` (BRIEF.md row 6). EPSG, cell size and the model's weights name come
  from the config.
- **Why.** `configs/landslide.json` has no keys for them, and P1-07 does not own the config (as in P1-03 D-new-10).
- **Alternatives.** Add a `sources` block to the config (P1-02 or P1-16): `susceptibility.service`,
  `susceptibility.alpha_min`, `susceptibility.classes`, `zabaged.service`, `zabaged.layers`.
